# Developer OS

## Product Vision, Architecture Blueprint и Roadmap

**Версия:** 0.4\
**Статус:** Product / Architecture Draft\
**Основной рабочий интерфейс:** DeepSeek Harness (DSH)\
**Основной пользователь:** разработчик-одиночка, управляющий несколькими
проектами и AI-исполнителями

------------------------------------------------------------------------

## 1. Краткое описание

**Developer OS** --- персональная composable-инженерная среда, которая
объединяет привычные инструменты разработчика в единый AI-enabled
рабочий процесс.

Система не должна заменять существующие инструменты управления знаниями,
задачами, кодом, сборками и инфраструктурой. Вместо этого она связывает
их между собой, предоставляет агентам контролируемый доступ к
возможностям этих инструментов и даёт человеку единое рабочее
пространство.

Основная идея:

> Developer OS не должна заставлять разработчика переходить на новый
> набор инструментов. Она должна сделать уже привычные инструменты
> согласованной средой совместной работы человека и AI-агентов.

DSH используется как основной интерфейс взаимодействия с агентами и как
основной execution harness на первом этапе. При этом архитектура
Developer OS не должна зависеть от DSH: в будущем отдельные runtime и
интерфейсы должны заменяться без переписывания бизнес-логики.

### Целевой результат

Один разработчик может управлять несколькими продуктами, их знаниями,
задачами, кодом, проверками и поставкой, не превращаясь в диспетчера
разрозненных AI-сессий.

Инженерный опыт накапливается между всеми проектами: каждый проект может
использовать общие знания и опубликованные решения, предлагать свой вклад
и сообщать об изменениях инфраструктуры и общих компонентов. Механизм
«Фиксация знаний» превращает полезный результат работы в проверенное
предложение для общей базы знаний или библиотеки.

## 2. Продуктовые принципы

### 2.1. Human-First

Все аспекты работы Developer OS должны укладываться в привычный ритм
разработчика и быть удобными прежде всего человеку.

-   Не заставлять человека менять привычный таск-трекер, базу знаний или
    Git-процесс.
-   Не делать чат единственным интерфейсом для всех операций.
-   Давать человеку возможность просматривать, понимать, редактировать и
    утверждать результаты работы агентов.
-   Сохранять прозрачность: человек должен понимать, что происходит,
    почему и в каком инструменте.
-   Автоматизировать рутину, но не скрывать важные решения и
    последствия.

### 2.2. Composable

Каждый функциональный блок должен подключаться, отключаться и заменяться
независимо.

-   Интеграции подключаются как плагины, MCP-серверы или адаптеры.
-   Система не должна требовать наличия всех интеграций.
-   Отсутствие одного сервиса не должно ломать остальные сценарии.
-   Конкретные инструменты выбираются конфигурацией пользователя.

### 2.3. MCP-First, но не MCP-Only

MCP --- основной стандартизированный интерфейс для предоставления
внешних возможностей AI-агентам.

При этом MCP не следует использовать для любой интеграционной задачи без
разбора.

Предпочтительные механизмы:

  Сценарий                                   Предпочтительный механизм
  ------------------------------------------ -----------------------------
  Агент ищет, читает или изменяет документ   MCP
  Агент создаёт или обновляет задачу         MCP
  Агент выполняет действие в Git-платформе   MCP или API
  Получение уведомления о завершении CI      Webhook
  Поток логов и событий                      Streaming API
  Обновление визуального интерфейса          WebSocket / SSE
  Человек просматривает CI/CD                UI + API
  Запуск опасной операции                    API/MCP с Policy и Approval

MCP --- интерфейс взаимодействия агента с инструментами, а не
универсальный UI-, event- или streaming-протокол.

### 2.4. Single Source of Truth

Каждая внешняя система остаётся владельцем своих данных.

Примеры:

-   DocWiki владеет документацией и знаниями.
-   Task Tracker владеет задачами и их статусами.
-   Git-платформа владеет репозиториями, ветками, PR и issue.
-   Общая документация хранится в DocWiki, повторно используемые артефакты
    — в Git и, при необходимости, пакетных/контейнерных реестрах.
-   CI/CD-платформа владеет результатами сборок и deployment.
-   DSH или другой runtime владеет внутренним состоянием своих агентных
    сессий.

Developer OS может хранить ссылки, идентификаторы, конфигурацию, кэш и
агрегированное представление. Она не должна создавать конкурирующие
копии исходных данных.

### 2.5. Agent-Agnostic

Бизнес-логика, данные и пользовательские сценарии не должны зависеть от
конкретной модели или harness.

DSH --- основной runtime на первом этапе, но не обязательная часть
доменной модели.

### 2.6. Safe by Design

-   Технические ограничения важнее решений LLM.
-   Доступ к файлам, сети, секретам и внешним сервисам должен быть
    ограничен.
-   Опасные действия требуют явной политики и, где необходимо,
    подтверждения человека.
-   Все значимые действия должны быть аудируемыми.
-   Результаты внешних инструментов и содержимое сайтов считаются
    недоверенными данными.

------------------------------------------------------------------------

### 2.7. Языковая политика проекта

-   Основная проектная документация, концепция продукта (Product Vision),
    архитектурный план (Architecture Blueprint), записи архитектурных решений
    (ADR) и пользовательские инструкции ведутся на русском языке. Перевод
    возможен при локализации документа целиком.
-   Пользовательский интерфейс должен поддерживать несколько языков.
    Русский и английский должны быть предусмотрены как минимум на уровне
    архитектуры локализации.
-   API, имена модулей, классов, функций, переменных, событий, MCP tools,
    конфигурационных ключей и другие технические идентификаторы оформляются
    на английском языке.
-   Технические идентификаторы не переводятся в русскоязычной документации,
    если перевод может нарушить однозначность или затруднить поиск по коду.
-   В русскоязычной документации и интерфейсе используются понятные русские
    названия функциональности. При необходимости при первом упоминании
    можно указать английский термин и технический идентификатор.
-   Для механизма `Knowledge Capture` основное русское название —
    **«Фиксация знаний»**.
-   Язык пользовательского интерфейса не должен определять язык API
    или внутренней модели данных.
-   Названия файлов документации оформляются на русском языке.
    Служебные точки входа `README.md` и `AGENTS.md` сохраняют стандартные
    имена для инструментов; это не меняет язык их содержимого.

## 3. Целевая архитектура

Developer OS состоит из трёх логических уровней.

``` text
┌──────────────────────────────────────────────────────────────┐
│                       WORKBENCH LAYER                        │
│                                                              │
│  DSH TUI / Web · Agent Sessions · Human Approval             │
│  Visual Dashboards · Notifications · Developer Interaction  │
└──────────────────────────────┬───────────────────────────────┘
                               │
┌──────────────────────────────▼───────────────────────────────┐
│               INTEGRATION & ORCHESTRATION LAYER              │
│                                                              │
│  MCP Gateway          Plugin Registry       Runtime Adapters │
│  Workflow Engine      Event Router          Context Assembly │
│  Security Policies    Approval Handling     Integration API  │
└──────────────────────────────┬───────────────────────────────┘
                               │
┌──────────────────────────────▼───────────────────────────────┐
│                     EXTERNAL TOOLS LAYER                     │
│                                                              │
│  DocWiki · Task Tracker · Git · DSH/Codex · CI/CD            │
│  Docker · Monitoring · Browser · Custom Services             │
└──────────────────────────────────────────────────────────────┘
```

### 3.1. Workbench Layer

Основная среда взаимодействия человека и AI-агентов.

На первом этапе это DSH TUI/Web и плагины, расширяющие его возможности.

Ответственность:

-   запуск и управление агентными сессиями;
-   выбор проекта и контекста;
-   просмотр задач и состояния работы;
-   подтверждение важных действий;
-   отображение результатов, diff и проверок;
-   визуальные панели для вспомогательных инженерных систем.

### 3.2. Integration & Orchestration Layer

Связывает внешние инструменты, события, агентов и процессы.

Основные компоненты:

-   **MCP Gateway** --- доступ агентов к внешним возможностям;
-   **Plugin Registry** --- подключаемые интеграции и расширения;
-   **Runtime Adapters** --- унифицированный доступ к разным agent
    runtime;
-   **Workflow Engine** --- управление последовательностями и
    состояниями процессов;
-   **Event Router** --- обработка webhook, событий и уведомлений;
-   **Context Assembly** --- сборка контекста проекта и задачи;
-   **Security Policies** --- правила доступа, approvals и аудит;
-   **Integration API** --- интерфейсы для визуальных компонентов и
    внешних клиентов.

### 3.3. External Tools Layer

Внешние продукты остаются самостоятельными системами. Developer OS
связывает их, но не пытается переписать.

## 4. Функциональные направления

### 4.1. Portfolio & Knowledge Management

**Основная система знаний: DocWiki (`docwiki.ru`).**

DocWiki --- внешний источник истины для документации, знаний,
архитектурных решений и проектного контекста.

Developer OS и агенты должны взаимодействовать с DocWiki через MCP.

#### Требуемые возможности

-   поиск документов;
-   чтение документов;
-   создание документов;
-   редактирование документов;
-   просмотр связей между документами;
-   навигация по пространствам и проектам;
-   доступ к истории изменений, если это поддерживается DocWiki;
-   поиск по глобальным и проектным знаниям.

#### Предлагаемая структура знаний

-   **Global Engineering Knowledge** --- общие инженерные принципы и
    соглашения;
-   **Project Knowledge** --- документация конкретных продуктов;
-   **Architecture Decisions** --- ADR и архитектурные решения;
-   **Agent Knowledge** --- инструкции, правила и ограничения для
    агентов;
-   **Operational Knowledge** --- инфраструктура, deployment, CI/CD и
    эксплуатация.

Документы должны оставаться удобными для чтения и редактирования
человеком. Не следует превращать всю базу знаний в набор машинных
JSON-объектов.

#### Human approval для документации

Изменения, созданные агентом, должны быть доступны человеку для
просмотра. Для существенных архитектурных документов желательно
предусмотреть diff и процесс принятия/отклонения изменений.

#### Важное ограничение

Не создавать параллельную базу знаний внутри Developer OS. Локально
можно хранить ссылки, идентификаторы, временный кэш и контекст сессий,
но DocWiki остаётся владельцем документов.

### 4.1.1. Общая инженерная память и фиксация знаний

#### Общий принцип

Developer OS должна обеспечивать накопление и повторное использование
инженерного опыта между всеми проектами.

Любой проект может:

-   получать общие знания и повторно использовать опубликованные компоненты
    и решения;
-   предлагать полезные результаты своей работы для включения в общую базу
    знаний или библиотеку;
-   сообщать об изменениях в инфраструктуре и общих компонентах, которые
    могут быть полезны другим проектам.

Для этого вводится механизм **«Фиксация знаний»**: пользователь может
естественным языком попросить агента сохранить результат работы для
повторного использования, например: «Зафиксируй это в общей базе знаний»
или «Положи результат в общую библиотеку».

Агент определяет тип результата, собирает необходимые файлы и контекст,
отделяет общую часть от проектно-специфичной, проверяет безопасность и
полноту, готовит предложение публикации и показывает его человеку.
Публикация в общую базу знаний или библиотеку выполняется после утверждения.

#### Общая база знаний и общая библиотека

Следует разделять два взаимосвязанных хранилища:

-   **Общая база знаний** — инструкции, стандарты, архитектурные решения,
    объяснения и эксплуатационный опыт. Основное хранилище — DocWiki.
-   **Общая библиотека** — исходный код, UI-компоненты, шаблоны проектов,
    конфигурации, скрипты, CI/CD workflows, плагины и другие повторно
    используемые артефакты. Основное хранилище — Git и при необходимости
    пакетные/контейнерные реестры.

Для каждого опубликованного элемента сохраняются описание, тип, версия,
статус, совместимость, происхождение, ссылки на документацию и исходные
артефакты. Developer OS ведёт каталог метаданных и связей, сохраняя
владение содержимым за DocWiki, Git и реестрами.

#### Инфраструктурные проекты как источники общих решений

Инфраструктурные проекты могут выступать центрами компетенций и
первоисточниками проверенных решений: Docker, сети, базы данных, CI/CD,
deployment, мониторинг, безопасность и эксплуатация.

Необходимо различать:

-   эталонные инфраструктурные проекты, содержащие повторно используемые
    решения;
-   операционные инфраструктурные проекты, управляющие реальными
    окружениями и ресурсами.

Изменения в продуктовом или операционном проекте могут предлагаться в
качестве вклада в эталонный инфраструктурный проект, но не должны
автоматически становиться общим стандартом.

#### Распространение обновлений

Developer OS отслеживает связи проектов с общими документами, компонентами
и шаблонами. После публикации новой версии система:

1.  Определяет проекты-потребители.
2.  Анализирует потенциальное влияние и совместимость.
3.  Уведомляет затронутые проекты.
4.  При необходимости создаёт задачи или предложения PR.
5.  Помогает агенту подготовить обновление.
6.  Сохраняет сведения о принятой версии.

Информация о новых версиях может распространяться автоматически.
Изменения кода, конфигураций и работающей инфраструктуры применяются только
через проверки и предусмотренные политики подтверждения. Публикация новой
версии сама по себе не обновляет проекты-потребители.

#### Подробная спецификация

Понятия, категории результатов, процесс фиксации, статусы, версии,
зависимости, инструменты агентов, безопасность, этапы реализации и
критерии готовности описаны в
[«Фиксация знаний»](docs/Фиксация%20знаний.md).

### 4.2. Task Orchestration

Использовать привычный внешний Task Tracker вместо разработки
собственного таск-менеджера.

Потенциальные интеграции:

-   YouTrack;
-   Linear;
-   GitHub Issues / Projects;
-   GitLab Issues;
-   другие системы, которые пользователь сможет подключить.

Конкретный трекер не фиксируется на этапе проектирования. Интеграция
должна быть заменяемой.

#### Базовые операции

-   получить список проектов;
-   получить задачи проекта;
-   найти задачу;
-   создать задачу;
-   изменить статус;
-   добавить комментарий;
-   установить исполнителя и приоритет;
-   получить зависимости;
-   связать задачу с PR, документом или execution session;
-   получить историю изменений, если API это позволяет.

#### Принцип владения данными

Task Tracker остаётся источником истины для задач. Developer OS может
агрегировать данные и сохранять внешние идентификаторы, но не должна
поддерживать независимую конкурирующую копию задач.

#### Оркестрация

Task Manager и Workflow Engine --- разные ответственности:

-   Task Tracker отвечает за то, **что нужно сделать**.
-   Orchestrator отвечает за то, **как организовать выполнение**.

### 4.3. Agent Execution

**Основной runtime на первом этапе: DeepSeek Harness (DSH).**

DSH используется как основная среда запуска, управления и взаимодействия
с агентами.

При этом интеграция должна быть построена так, чтобы в будущем можно
было подключить другие runtime:

-   Codex;
-   Pi;
-   OpenCode;
-   OpenHands;
-   другие совместимые решения.

#### Управление жизненным циклом

-   создание сессии;
-   выбор runtime и модели;
-   выбор проекта и рабочей директории;
-   передача задачи;
-   сборка и передача контекста;
-   подключение инструментов и MCP;
-   получение событий;
-   прерывание;
-   завершение;
-   сохранение ссылок на результаты и артефакты;
-   восстановление состояния после перезапуска Developer OS, насколько
    это поддерживает runtime.

#### Runtime Abstraction

Внутренние модули Developer OS не должны напрямую зависеть от API
конкретного harness.

Пример концептуального контракта:

``` typescript
interface AgentRuntime {
  readonly id: string;

  capabilities(): Promise<RuntimeCapabilities>;

  startSession(
    input: StartSessionInput
  ): Promise<AgentSession>;

  sendMessage(
    sessionId: string,
    message: string
  ): Promise<void>;

  interrupt(
    sessionId: string
  ): Promise<void>;

  getSession(
    sessionId: string
  ): Promise<AgentSessionState>;

  getEvents(
    sessionId: string
  ): AsyncIterable<AgentEvent>;

  terminate(
    sessionId: string
  ): Promise<void>;
}
```

Это предварительный контракт. Его нужно уточнить после исследования
реальных возможностей DSH SDK, CLI и событийной модели.

Если SDK не предоставляет нужных возможностей, допускается отдельный
адаптер через CLI или другой поддерживаемый интерфейс.

### 4.4. Quality & Security

DSH может управлять процессом проверок и запускать специализированных
агентов, но качество и безопасность не должны полностью зависеть от LLM.

Три уровня:

#### A. AI-based checks

-   анализ diff;
-   независимое code review;
-   проверка соответствия требованиям;

## 6. Визуальный язык и UX

### 6.1. Самостоятельное визуальное направление

Developer OS использует собственную визуальную систему: аккуратную
типографику, ясную иерархию, спокойные поверхности, выразительные акценты
и понятное представление инженерных процессов.

Для лендинга выбрана тёмная графитовая основа с двумя акцентными цветами:
синий #779BFF для действий и орхидея #E6A3ED для общей памяти и повторного
использования. Кнопка с двухцветным кругом справа сверху, без стрелки,
переключает орхидею и мятный #69DFC5. По умолчанию используется орхидея;
жёлтый исключён из переключателя по решению владельца от 16.11.2026.
Схемы, инфографика и статусы используют самостоятельные смысловые цвета:
например, зелёные круги с галочками обозначают завершённые этапы. Изменение
палитры страницы не меняет семантику статусов. Цвет дополняется подписью
или символом, чтобы смысл оставался понятным без различения оттенков.
В концепции, текстах и макетах не указывать названия и ссылки на сторонние
дизайн-референсы; их фирменные элементы не копировать.

### 6.2. Ожидаемые свойства интерфейса

-   чистый, современный, минималистичный интерфейс;
-   понятная визуальная иерархия;
-   аккуратная типографика;
-   продуманная система отступов и размеров;
-   умеренное использование карточек и разделителей;
-   ясные статусы и индикаторы прогресса;
-   хорошо различимые стадии workflow;
-   визуально понятные связи между задачами и агентными сессиями;
-   отсутствие перегруженности декоративными элементами;
-   единообразие всех разработанных панелей и плагинов;
-   качественная поддержка светлой и тёмной темы;
-   адаптация к размерам окна и терминального/web-интерфейса DSH.

### 6.3. Принципы визуализации

-   Статус должен считываться быстро и без необходимости читать длинное
    описание.
-   Цвет использовать семантически, а не декоративно.
-   Важные ошибки и запросы подтверждения должны быть заметны, но не
    превращать весь интерфейс в набор ярких предупреждений.
-   Сложные процессы показывать через последовательность стадий,
    зависимости и состояние выполнения.
-   Детали раскрывать по запросу, не перегружая основной экран.
-   Визуальные компоненты должны быть функциональными, а не просто
    демонстрационными.

### 6.4. Ограничения

-   Не копировать логотип, фирменную графику или уникальные брендовые
    элементы сторонних продуктов.
-   Не воспроизводить интерфейс пиксель-в-пиксель.
-   Сохранять совместимость с визуальными и техническими conventions
    DSH.
-   Развивать самостоятельный визуальный язык и проверять
    композицию и палитру на собственных сценариях Developer OS.

Перед реализацией первых визуальных плагинов следует подготовить
небольшой UI Style Guide с цветами, типографикой, отступами, карточками,
статусами, формами и состояниями компонентов.

## 7. Integration Strategy

MCP-first не означает MCP-only.

Для каждой интеграции нужно выбирать подходящий механизм.

  Интеграция        Основной механизм        Дополнительный механизм
  ----------------- ------------------------ ---------------------------------
  DocWiki           MCP                      API
  Task Tracker      MCP                      Webhook / API
  GitHub / GitLab   MCP                      API / Webhook
  CI/CD             API                      Webhook / Streaming
  Monitoring        API                      Webhook / Streaming
  Docker            MCP или native adapter   Docker API
  Browser           MCP / Browser API        Локальный или удалённый browser
  Agent Runtime     Runtime Adapter          CLI / SDK / ACP

### 7.1. Требования к интеграциям

Каждая интеграция должна иметь:

-   явное описание возможностей;
-   конфигурацию подключения;
-   проверку доступности;
-   обработку ошибок;
-   правила авторизации;
-   управление секретами;
-   таймауты и retry policy;
-   логирование;
-   документацию;
-   возможность отключения без поломки системы.

### 7.2. Capability Discovery

Желательно, чтобы система могла определять возможности подключённого
инструмента.

Например, один Task Tracker может поддерживать зависимости задач, другой
--- нет. Developer OS не должна предполагать наличие возможностей,
которых фактически нет.

Агенты должны получать корректное описание доступных операций.

Фиксация знаний использует интеграции DocWiki, Git и реестров для поиска,
подготовки и публикации утверждённых результатов. События новых версий
и проверки обновлений связываются с проектами-потребителями и внешним
Task Tracker. Предварительные инструменты агента и границы операций
описаны в [спецификации фиксации знаний](docs/Фиксация%20знаний.md);
их доступность в конкретном коннекторе должна проверяться.

## 8. Источники истины и локальное состояние

Developer OS не должна дублировать внешние системы.

Однако ей потребуется собственное минимальное состояние для связывания
инструментов и управления процессами.

Предлагаемые локальные сущности:

-   `ExternalConnection` --- подключённая система;
-   `ExternalResourceRef` --- ссылка на внешний объект;
-   `ProjectBinding` --- связи проекта с репозиторием, DocWiki и Task
    Tracker;
-   `RuntimeSessionRef` --- ссылка на сессию агента;
-   `WorkflowExecution` --- состояние процесса;
-   `ApprovalRecord` --- история подтверждений;
-   `IntegrationEvent` --- полученные события;
-   `AuditRecord` --- журнал значимых действий.

Для общей инженерной памяти дополнительно нужны метаданные элементов
библиотеки, ссылки на их версии и происхождение, предложения публикации
и зависимости проектов от общих решений с принятой версией и политикой
обновления. Окончательная схема определяется при техническом проектировании
по [спецификации фиксации знаний](docs/Фиксация%20знаний.md); содержимое
документов и артефактов остаётся во внешних хранилищах.

Локальное хранилище может использовать SQLite на первом этапе.

SQLite не должен превращаться в альтернативную базу знаний или
таск-трекер. Его задача --- хранить конфигурацию, связи, состояние
оркестрации и техническую историю Developer OS.

## 9. MVP Roadmap

Реализация должна идти небольшими этапами. Каждый этап должен приносить
самостоятельную пользу.

Общая инженерная память развивается по этапам из
[спецификации фиксации знаний, раздел 17](docs/Фиксация%20знаний.md):
ручная фиксация с просмотром и утверждением → Git-библиотека артефактов →
поиск и повторное использование → связи и распространение обновлений →
обратный вклад проектов. Это сквозное направление: оно опирается на
DocWiki Integration, Project Context, Agent Workflow, Quality & Security
и Event-Driven Automation. Порядок конкретных задач уточняется в blueprint;
полная автоматизация не является условием первого полезного среза.

### Phase 0. DSH Foundation

Цель: проверить DSH как рабочую среду и платформу расширений.

-   изучить актуальную архитектуру DSH;
-   проверить Plugin API и Cordis;
-   изучить MCP client;
-   проверить SDK, CLI, headless и event capabilities;
-   проверить возможности UI-плагинов;
-   определить способ распространения и конфигурации плагинов;
-   зафиксировать ограничения и риски.

**Результат:** технический blueprint интеграции с DSH.

### Phase 1. DocWiki Integration

Первая реальная интеграция.

-   подключить DocWiki через MCP;
-   проверить поиск, чтение, создание и редактирование документов;
-   определить структуру пространств и проектных знаний;
-   обеспечить передачу ссылок на документы в контекст агента;
-   проверить совместную работу человека и агента с документацией;
-   определить процесс просмотра и утверждения изменений.

**Результат:** DSH-агент может полноценно работать с DocWiki, а человек
может просматривать и редактировать те же документы.

### Phase 2. Task Tracker Integration

-   выбрать первый трекер;
-   подключить его через MCP;
-   реализовать поиск и чтение задач;
-   создание и обновление задач;
-   получение зависимостей;
-   связывание задач с проектами, документами и репозиториями;
-   определить правила синхронизации и владения данными.

**Результат:** агент работает с реальными задачами разработчика, не
создавая параллельный таск-менеджер.

### Phase 3. Project Context

Автоматическая сборка контекста задачи.

Контекст может включать:

-   описание проекта;
-   ссылки на репозиторий;
-   документацию DocWiki;
-   связанные архитектурные решения;
-   задачу из Task Tracker;
-   инженерные правила;
-   состояние Git;
-   предыдущие результаты работы.

**Результат:** разработчик не объясняет устройство проекта при каждом
новом запуске агента.

### Phase 4. Agent Workflow

-   создание сессии DSH;
-   передача задачи и контекста;
-   получение событий;
-   управление сессией;
-   прерывание;
-   сохранение результатов;
-   просмотр diff;
-   ручная приёмка;
-   обновление статуса задачи после принятия результата.

**Результат:** полноценный цикл выполнения задачи через DSH.

### Phase 5. Quality & Security

-   тесты и линтеры;
-   независимый AI Reviewer;
-   security policies;
-   sandbox;
-   approval gates;
-   audit log;
-   проверка изменений перед принятием;
-   контроль сетевых и файловых полномочий.

**Результат:** контролируемое делегирование работы агентам.

### Phase 6. Visual Extensions

-   Git Dashboard;
-   CI/CD Dashboard;
-   Agent Session Dashboard;
-   Infrastructure Dashboard;
-   Monitoring Dashboard;
-   единая самостоятельная визуальная система Developer OS.

**Результат:** человеку удобно наблюдать и управлять инженерными
процессами визуально, а не только через чат.

### Phase 7. Event-Driven Automation

-   обработка webhook;
-   события CI/CD;
-   уведомления о сбоях;
-   автоматическое обнаружение проблем;
-   подготовка следующих задач;
-   периодические проверки;
-   фоновые процессы с ограниченными полномочиями.

**Результат:** Developer OS помогает поддерживать процесс разработки без
постоянного ручного запуска каждой операции.

### Phase 8. Runtime Expansion

-   оценка альтернативных runtime;
-   подключение Codex, Pi или OpenCode;
-   проверка совместимости Runtime Interface;
-   выбор исполнителя по типу задачи и возможностям;
-   сохранение независимости от конкретного harness.

**Результат:** возможность менять и комбинировать исполнителей без
изменения основной архитектуры.

## 11. Критерии успешного MVP

Первый MVP можно считать успешным, если разработчик способен:

1.  Подключить DSH и DocWiki.
2.  Найти и прочитать документацию проекта через агента.
3.  Создать или обновить документ через агента.
4.  Просмотреть изменения и отредактировать их самостоятельно.
5.  Подключить внешний Task Tracker.
6.  Найти задачу и передать её агенту.
7.  Автоматически собрать релевантный проектный контекст.
8.  Выполнить задачу в DSH.
9.  Получать события и видеть состояние выполнения.
10. Запустить проверки и получить результат.
11. Просмотреть diff и принять или отклонить работу.
12. Сохранить ссылки на результат в Task Tracker и DocWiki.
13. Перезапустить DSH/Developer OS и продолжить работу с доступным
    состоянием.
14. Попросить зафиксировать полезный результат, получить проверенное
    предложение с составом и назначением публикации, утвердить или
    отклонить его; после публикации найти знание из другого проекта.

Версионируемая библиотека артефактов, учёт потребителей и распространение
обновлений принимаются по этапам и критериям отдельной
[спецификации фиксации знаний](docs/Фиксация%20знаний.md).

Главный критерий: система должна быть полезна в повседневной разработке,
а не только в демонстрационном сценарии.

## 12. Инженерные требования к реализации

### Архитектура

-   TypeScript как основной язык, если исследование DSH не выявит
    существенных ограничений;
-   модульная архитектура;
-   минимум собственного backend-кода;
-   независимые интеграции;
-   явные контракты между модулями;
-   отсутствие прямой зависимости доменной логики от DSH API.
-   архитектура локализации пользовательского интерфейса с поддержкой
    русского и английского языков; API и внутренние идентификаторы
    остаются независимыми от выбранного языка интерфейса.

### Разработка

-   сначала исследование актуального DSH API и документации;
-   затем архитектурный blueprint;
-   затем небольшие вертикальные срезы;
-   TDD для новой бизнес-логики;
-   интеграционные тесты на границах MCP и внешних API;
-   фиксация решений в ADR;
-   документация рядом с реализацией.

### Надёжность

-   таймауты;
-   retry policy;
-   идемпотентность операций, где это необходимо;
-   обработка неизвестного результата после сетевого timeout;
-   восстановление состояния после перезапуска;
-   понятные ошибки;
-   журналирование действий.

### Безопасность

-   не хранить секреты в документации и логах;
-   использовать безопасное хранилище секретов;
-   минимальные полномочия для каждого инструмента;
-   разделять read и write операции;
-   ограничивать доступ к файловой системе и сети;
-   подтверждать критические действия;
-   считать внешние данные недоверенными.

## 15. Ключевая формулировка продукта

> Developer OS --- это composable-инженерная среда, объединяющая
> привычные инструменты разработчика, знания, задачи, AI-агентов,
> проверки и инфраструктуру в единый управляемый процесс.
>
> Она не заменяет существующие инструменты, а делает их совместную
> работу удобной для человека и доступной для AI-агентов.
>
> DSH выступает основным рабочим интерфейсом и execution harness на
> первом этапе. Все интеграции и функциональные компоненты остаются
> подключаемыми и заменяемыми.
>
> Главный принцип: человек сохраняет контроль и понимание происходящего,
> а агенты получают возможность выполнять полезную работу в рамках
> прозрачных полномочий и проверяемых процессов.
>
> Опыт каждого проекта может пополнять общую инженерную память.
> Фиксация знаний помогает подготовить и утвердить полезный результат,
> а другие проекты — найти его, повторно использовать и осознанно
> принять последующие обновления.
