# Принцип фиксации и повторного использования общих знаний

**Проект:** Developer OS  
**Версия:** 1.1  
**Статус:** Архитектурный принцип  
**Язык документации:** русский

## 1. Назначение

Developer OS должна помогать накапливать инженерный опыт между проектами. Полезные результаты разработки не должны оставаться изолированными в проекте, где они появились.

К таким результатам относятся:

- архитектурные решения и технические подходы;
- инструкции, стандарты и проверенные процедуры;
- инфраструктурные конфигурации;
- UI-компоненты и библиотеки;
- шаблоны проектов и готовые решения;
- Docker- и CI/CD-конфигурации;
- скрипты, пакеты, MCP-инструменты и плагины;
- навыки и инструкции для AI-агентов;
- решения типовых проблем и накопленный опыт.

**Основной принцип: каждый проект может получать общие знания и повторно использовать готовые решения, а также предлагать проверенные результаты своей работы для включения в общую инженерную базу и библиотеку.**

Пользователь должен иметь возможность запустить процесс естественным языком:

- «Зафиксируй это в общей базе знаний».
- «Положи результат в общую библиотеку».
- «Сохрани этот компонент для других проектов».
- «Подготовь из этого общий шаблон».
- «Найди похожее решение в общей библиотеке».

Фиксация знаний — не копирование текста диалога или случайных файлов. Агент должен выделить самостоятельный результат, обобщить его, описать ограничения и подготовить к повторному использованию.

## 2. Основные понятия

### 2.1. Общая база знаний

Содержит стандарты, инструкции, архитектурные паттерны, решения, ограничения, эксплуатационные знания и уроки, полученные в ходе разработки.

**Основное хранилище документации — DocWiki.** DocWiki остаётся источником истины для документов. Developer OS и агенты взаимодействуют с ним через MCP и доступные API, не создавая параллельную базу знаний.

### 2.2. Общая библиотека

Содержит повторно используемые артефакты:

- исходный код компонентов и UI-библиотек;
- HTML-каталоги компонентов и примеры;
- шаблоны проектов;
- Docker- и инфраструктурные конфигурации;
- CI/CD workflows;
- скрипты и пакеты;
- MCP-серверы, плагины и навыки агентов.

Основное хранилище исполняемых артефактов — Git-репозитории и, при необходимости, пакетные или контейнерные реестры.

### 2.3. Шаблон решения

Версионируемый набор кода, конфигураций, документации и инструкций, предназначенный для повторного применения. Например, шаблон Node.js-сервиса с UI-kit, Docker и CI/CD.

### 2.4. Фиксация знаний

Процесс извлечения полезного результата из текущего проекта, подготовки, проверки, публикации и регистрации его в общей базе знаний или библиотеке.

### 2.5. Вклад проекта

Предложение добавить или обновить общий документ, компонент, шаблон или другое решение на основании опыта конкретного проекта.

## 3. Откуда поступают общие знания

### 3.1. Инфраструктурные проекты

Инфраструктурные проекты — основные источники общих инфраструктурных решений: Docker, сети, reverse proxy, базы данных, резервное копирование, CI/CD, deployment, мониторинг, безопасность и эксплуатация.

Они содержат реальные конфигурации, код, документацию, тесты и историю изменений и могут выступать центрами компетенций.

### 3.2. Продуктовые проекты

Любой продуктовый проект может предложить общий результат: UI-библиотеку, универсальный компонент, удачную интеграцию API, скрипт миграции, улучшение мониторинга или решение повторяемой проблемы.

### 3.3. Отдельные задачи

Источником вклада может быть задача, исследование, эксперимент, исправление ошибки или агентная сессия.

По возможности сохраняется происхождение результата: исходный проект, задача, репозиторий, commit или PR, автор/агент и дата.

## 4. Категории фиксируемых результатов

| Категория | Содержание | Основное хранилище |
|---|---|---|
| Знание | Инструкции, объяснения, решения, опыт | DocWiki |
| Компонент | Код, UI-компоненты, библиотеки, скрипты | Git / Registry |
| Шаблон решения | Код, конфигурации и инструкции | Git / Registry + DocWiki |
| Навык агента | Повторяемая процедура и инструкции | Git / DSH Skills |
| Инфраструктурное решение | Конфигурации, код, эксплуатационная документация | Инфраструктурный проект + Git + DocWiki |

Один результат может включать несколько категорий. Например, UI-библиотека может состоять из исходного кода, HTML-каталога, инструкции по установке и навыка агента по созданию новых компонентов в принятом стиле.

## 5. Процесс фиксации знаний

Процесс должен быть доступен из любой агентной сессии Developer OS и запускаться естественным языком.

### Этапы

1. **Получение запроса.** Агент определяет, какой результат пользователь хочет сохранить.
2. **Анализ результата.** Изучает файлы, изменения, документы, задачу и историю работы.
3. **Классификация.** Определяет тип результата.
4. **Извлечение.** Собирает необходимые файлы, примеры, документацию, зависимости и контекст.
5. **Обобщение.** Отделяет повторно используемую часть от проектно-специфичных значений.
6. **Проверка качества.** Проверяет полноту, воспроизводимость, совместимость, лицензии и безопасность.
7. **Подготовка публикации.** Создаёт описание, метаданные, структуру и предложение версии.
8. **Представление человеку.** Показывает, что именно будет опубликовано и куда.
9. **Утверждение.** Получает подтверждение пользователя или владельца общей библиотеки.
10. **Публикация.** Документация отправляется в DocWiki, файлы — в Git-библиотеку, метаданные — в каталог Developer OS.
11. **Связывание.** Сохраняет ссылки на исходный проект, задачу, commit и опубликованные материалы.

### Проверки перед публикацией

Агент должен проверить:

- секреты, токены, пароли и приватные данные;
- абсолютные пути и локальные настройки;
- применимость вне исходного проекта;
- зависимости и требования совместимости;
- лицензии и права на повторное использование;
- наличие документации и примеров;
- наличие аналогичного решения в библиотеке;
- завершённость и проверенность результата.

Экспериментальные результаты можно сохранять как черновики, но нельзя автоматически публиковать как стабильные решения.

## 6. Статусы и жизненный цикл

| Статус | Значение |
|---|---|
| Черновик (`draft`) | Подготовлено, но не проверено |
| На проверке (`in_review`) | Ожидает проверки или утверждения |
| Утверждено (`approved`) | Разрешено к публикации |
| Опубликовано (`published`) | Доступно для поиска и повторного использования |
| Устарело (`deprecated`) | Не рекомендуется для новых применений |
| Архивировано (`archived`) | Сохранено для истории |

Публикация новой версии не должна автоматически менять уже использующие её проекты.

## 7. Поиск и повторное использование

При работе над задачей или создании нового проекта агент должен:

1. Определить, какие знания и компоненты могут понадобиться.
2. Искать их в общей базе знаний и библиотеке.
3. Получать описание, документацию и ссылки на артефакты.
4. Проверять совместимость с текущим проектом.
5. Предлагать готовое решение вместо повторной разработки.
6. Подключать или копировать компонент по установленным правилам.
7. Сохранять сведения о версии и происхождении использованного решения.

Каталог должен поддерживать поиск по назначению, технологиям, тегам, совместимости и типу результата.

## 8. Инфраструктурные проекты как источники решений

Следует различать два типа инфраструктурных проектов.

### Эталонные инфраструктурные проекты

Содержат проверенные и повторно используемые решения: конфигурации, стандартные способы развёртывания, инфраструктурные модули, инструкции, reusable workflows и эксплуатационные процедуры.

### Операционные инфраструктурные проекты

Управляют реальными окружениями и ресурсами: production, staging, dev-серверами, сетями, базами данных и deployment.

Реальные конфигурации не следует автоматически считать универсальными шаблонами. Перед публикацией нужно отделить общую часть от параметров конкретного окружения.

Обновление эталонного решения не должно автоматически менять работающую инфраструктуру. Изменение operational infrastructure также не должно без проверки становиться новым общим стандартом.

## 9. Обратный вклад продуктовых проектов

Фиксация знаний работает в обе стороны.

Если в продуктовом проекте найдено полезное инфраструктурное или инженерное решение:

1. Агент или Developer OS обнаруживает потенциально общий характер изменения.
2. Агент предлагает вклад в соответствующий инфраструктурный проект или общую библиотеку.
3. Подготавливает описание проблемы, решение, ограничения и необходимые изменения.
4. Создаёт предложение на проверку.
5. После утверждения решение включается в эталонный проект и, при необходимости, публикуется как новая версия.

**Любой проект может предложить улучшение общей библиотеки, но не каждый проект может автоматически изменять её первоисточник.**

## 10. Версионирование и зависимости

Каждый опубликованный компонент или шаблон должен иметь стабильный идентификатор и версию.

Пример метаданных:

```yaml
id: ui.shared-components
name: Shared UI Kit
type: component
version: 1.0.0
status: published

source:
  project: product-a
  repository: product-a
  commit: abc123

storage:
  repository: engineering-assets
  path: ui/shared-components
  documentation: docwiki://engineering/ui-kit

tags:
  - ui
  - components
  - react

compatibility:
  frameworks:
    - react
```

Пример зависимости проекта:

```yaml
project: product-b

shared_dependencies:
  - id: ui.shared-components
    version: "^1.0"
    update_policy: propose_changes

  - id: infrastructure.docker.node-service
    version: "~2.3"
    update_policy: notify

  - id: engineering.typescript.standards
    version: "^1.4"
    update_policy: use_latest_approved_knowledge
```

Это концептуальный формат; окончательная схема определяется при техническом проектировании.

### Политики обновления

- **Использовать актуальные знания:** агент читает последнюю утверждённую редакцию документа.
- **Уведомлять:** проект получает информацию о новой версии.
- **Предлагать изменения:** готовится задача или PR.
- **Требовать подтверждение:** изменение не применяется без человека.
- **Зафиксированная версия:** проект продолжает использовать конкретную версию.

Документация и исполняемые компоненты могут иметь разные политики обновления.

## 11. Распространение обновлений

После публикации новой версии Developer OS определяет, какие проекты могут быть затронуты.

1. В общей библиотеке опубликовано изменение.
2. Developer OS получает событие или обнаруживает новую версию.
3. Находит проекты, использующие документ, компонент или шаблон.
4. Определяет политику обновления каждого проекта.
5. При необходимости анализирует совместимость.
6. Создаёт уведомления и задачи.
7. Агент может подготовить изменения в проекте.
8. Тесты и проверки подтверждают корректность.
9. Человек принимает или отклоняет изменения.
10. Developer OS обновляет сведения о применённой версии.

**Информация о новой версии может распространяться автоматически. Изменение кода, конфигурации или работающей инфраструктуры не должно происходить без соответствующих проверок и полномочий.**

## 12. Каталог общей библиотеки

Для каждого элемента каталога следует показывать:

- название и назначение;
- категорию и описание;
- опубликованную версию и статус;
- совместимость и теги;
- ссылку на документацию;
- ссылку на исходный код или артефакты;
- исходный проект;
- историю версий;
- список проектов-потребителей, если он известен.

Каталог доступен человеку в DSH Workbench и агентам через MCP-инструменты.

## 13. Инструменты для агентов

Предварительные английские технические идентификаторы:

| Tool | Назначение |
|---|---|
| `knowledge_search` | Поиск общих знаний |
| `asset_search` | Поиск компонентов и шаблонов |
| `knowledge_capture` | Подготовка фиксации результата |
| `knowledge_publish` | Публикация утверждённого результата |
| `knowledge_update` | Подготовка обновления существующего элемента |
| `knowledge_dependencies` | Поиск проектов, использующих элемент |
| `knowledge_impact` | Анализ влияния изменения |
| `knowledge_contribution` | Создание предложения из текущего проекта |

Это предварительный список. Не все операции обязательно должны быть отдельными MCP tools.

### Примеры естественных команд

- «Зафиксируй это в общей базе знаний».
- «Положи результат в общую библиотеку».
- «Сохрани этот компонент для других проектов».
- «Подготовь общий шаблон из текущего решения».
- «Найди похожее решение в общей библиотеке».
- «Проверь, какие проекты используют этот компонент».
- «Предложи обновление инфраструктурного шаблона».

## 14. Роли и ответственность

| Участник | Ответственность |
|---|---|
| Пользователь | Определяет, что сохранить, утверждает публикацию и важные обновления |
| Агент проекта | Находит, извлекает, обобщает и документирует результат |
| Developer OS | Управляет каталогом, связями, версиями, зависимостями и распространением |
| DocWiki | Хранит общую документацию |
| Git / Registry | Хранит исходный код и исполняемые артефакты |
| Инфраструктурные проекты | Поддерживают эталонные инженерные решения |
| Проверяющий агент или человек | Проверяет качество, применимость и безопасность вклада |

## 15. Языковая политика

- Основная проектная документация, Product Vision, Architecture Blueprint, ADR и пользовательские инструкции ведутся на русском языке. Перевод возможен при локализации документа целиком.
- Пользовательский интерфейс должен поддерживать несколько языков. Русский и английский должны быть предусмотрены как минимум на уровне архитектуры локализации.
- API, имена модулей, классов, функций, переменных, событий, MCP tools, конфигурационных ключей и другие технические идентификаторы оформляются на английском языке.
- Технические идентификаторы не переводятся в русскоязычной документации, если перевод может нарушить однозначность или затруднить поиск по коду.
- В русскоязычной документации и интерфейсе используются понятные русские названия функциональности. При необходимости при первом упоминании можно указать английский термин и технический идентификатор.
- Для механизма `Knowledge Capture` основное русское название — **«Фиксация знаний»**.
- Язык пользовательского интерфейса не должен определять язык API или внутренней модели данных.
- Названия файлов документации оформляются на русском языке. Стандартные служебные точки входа `README.md` и `AGENTS.md` сохраняют имена для инструментов.

## 16. Безопасность и ограничения

Перед публикацией проверять секреты, персональные и приватные данные, внутренние адреса и параметры окружений, лицензии, зависимости и проектно-специфичные значения.

Необходимо сохранять происхождение каждого результата. Публикация в общей библиотеке не должна автоматически предоставлять всем проектам права на изменение опубликованного элемента.

Для общих активов должны быть определены владельцы или правила сопровождения.

## 17. Этапы реализации

### Этап 1. Ручная фиксация знаний

- Подключить DocWiki через MCP.
- Создать общую структуру знаний.
- Определить типы фиксируемых результатов.
- Реализовать подготовку публикации агентом.
- Добавить просмотр и подтверждение человеком.

**Результат:** пользователь может попросить агента зафиксировать результат, проверить материалы и опубликовать их.

### Этап 2. Общая библиотека артефактов

- Создать Git-репозиторий общей библиотеки.
- Определить структуру хранения.
- Добавить каталог метаданных.
- Реализовать публикацию компонентов, шаблонов и навыков.
- Добавить версии и статусы.

**Результат:** готовые решения можно искать и повторно использовать в других проектах.

### Этап 3. Поиск и повторное использование

- Подключить поиск к контексту агента.
- Научить агента проверять наличие готовых решений перед разработкой.
- Добавить проверку совместимости.
- Сохранять сведения о версиях и происхождении.

**Результат:** новые проекты используют накопленный инженерный опыт.

### Этап 4. Связи и распространение обновлений

- Добавить Project Manifest.
- Ввести зависимости проектов от общих активов.
- Реализовать уведомления о новых версиях.
- Добавить анализ влияния изменений.
- Создавать задачи на обновление.

**Результат:** Developer OS знает, какие проекты используют общие решения и какие из них могут быть затронуты.

### Этап 5. Обратный вклад проектов

- Обнаруживать потенциально повторно используемые результаты.
- Предлагать вклад в общую библиотеку.
- Подготавливать изменения для инфраструктурных проектов.
- Проводить проверку и публикацию новых версий.

**Результат:** общая инженерная библиотека развивается за счёт опыта всех проектов.

## 18. Критерии готовности

Базовый механизм фиксации знаний реализован, если пользователь способен:

1. В любой агентной сессии попросить зафиксировать результат.
2. Получить предложение с типом и составом публикации.
3. Увидеть список файлов и документов, которые будут сохранены.
4. Проверить отсутствие секретов и ненужных проектных данных.
5. Утвердить или отклонить публикацию.
6. Получить опубликованный документ в DocWiki и/или артефакт в Git-библиотеке.
7. Найти результат из другого проекта.
8. Повторно использовать его с учётом версии и совместимости.
9. Узнать, какие проекты используют компонент.
10. Получать информацию о новых версиях и предлагать обновления.

## 19. Ключевой принцип

> Каждый проект может получать общие знания и повторно использовать проверенные решения. Каждый проект может предлагать полезные результаты своей работы для общей библиотеки. Публикация проходит через фиксацию, проверку и утверждение, а распространение обновлений учитывает зависимости и совместимость проектов.

**Фиксация знаний превращает разрозненный опыт отдельных проектов в общий инженерный актив, который сохраняет ценность и делает каждый следующий проект быстрее, дешевле и качественнее.**
